1. Introduction

1.1 Purpose

This Technical Design Document / Low-Level Design (TDD/LLD) spells out how the Dynamics Queue Admin console is built, down to the level where another engineer can open the right file and change a behaviour without guessing. It sits next to the SRS (which says what the system has to do) and the SDD (which says what the system looks like and why). Where the SDD names a component, this document names the file, the symbol and the control that implements it.

1.2 Scope

Scope is the queadmin-frontend single-page application (SPA) as built and submitted: the browser console that queue organization administrators (role 11), queue dispatchers (role 12), transport-company administrators (role 3) and transport-company staff (role 6) use to manage dispatch queues, organizations, members, shipper requests, bids and reports. The backend service transportBackEndNative is out of build scope, but we reference it wherever it is the point that actually enforces the rule; those spots are labelled Server or backend.

Mobile clients, the transportCompany SPA and infrastructure provisioning are out of scope, except where they show up as external actors of the console.

1.3 Audience

Three groups read this: INSA evaluation reviewers checking conformity to the Secure Website Management Standard, maintainers and reviewers of the queadmin-frontend codebase, and security assessors who need to separate the controls the browser enforces from the ones the server enforces. It assumes you already know React, TypeScript and HTTP.

1.4 Relationship to the SRS and SDD

The SRS requirement families are what traceability hangs off. The SDD (Section 12) maps those families to design elements: FR-AUTH, FR-ROLE/ACCESS, FR-ORG, FR-QUEUE, FR-BID, FR-ORDER, FR-REALTIME, FR-REPORT, plus the non-functional families NFR-SEC and NFR-DEPLOY. Section 9 of this document drills each family down to the component and handler level, and Section 15 maps derived controls to file-and-symbol evidence. We don't introduce a requirement family here that isn't already in the companion set.

1.5 Design principles and constraints

  • Server-authoritative security. The client enforces role and ownership rules for usability and defence in depth, but the backend is the authority. Client guards are never presented as the security boundary (see Section 13.3).
  • Cookie session, no token in JavaScript. The session JWT lives in an httpOnly cookie; JavaScript stores hold only a non-sensitive profile and no bearer token (Section 4.2).
  • Fail closed. Unknown or unauthenticated route states redirect to login rather than rendering a protected view (Section 5.2).
  • Defensive decoding. All backend payloads pass through decoders and schemas that tolerate absence and reject malformed values, so one bad record cannot crash a list (Section 7.3, Section 12.1).
  • Honesty over masquerade. Settings controls with no backend support are disabled rather than faked, and known gaps are recorded as open findings (Section 11.5, Section 15.3).
  • Build-gated quality. Type-check, lint and the unit suite are the release gates described in Section 3 and Section 14.

1.6 Conventions

Code paths are shown relative to the repository root. Line references (file.ts:NN) identify the as-built release and may shift by a few lines under reformatting; the enclosing symbol name is the durable reference. Controls are labelled Met, Open, By design or Server/Debt as defined in Section 15.1.

Open finding carried into the design (C3)

The API contract comment and the maintenance rule say that login and OTP verification send no roleId, so the backend resolves the account's own role and a role 12 dispatcher can sign in. The service as built still transmits roleId: 11 on both calls. That's recorded as an open finding (Section 4.1, C3), and it is the only client/contract divergence in the release.

2. Architecture-to-code map

This section ties the SDD's architectural view back to actual source files. It covers the system context (Level 0), the logical layers (Level 2), and the boot sequence that wires them together.

2.1 System context (Level 0)

The console is a browser SPA that talks to one backend service over HTTPS (REST) and WSS (Socket.IO). It authenticates through an httpOnly cookie issued by the backend, and every read or write touches backend-owned data. There is no direct database access and no third-party runtime integration.

External actor / system Direction Channel Purpose
Queue org admin (role 11) / dispatcher (role 12) In Browser Manage queue organizations, dispatch queue, members, bids.
Transport admin (role 3) / staff (role 6) In Browser Cross-organization administration and oversight.
transportBackEndNative REST API In / out HTTPS (JSON) All data reads and mutations; session issuance and authority.
Socket.IO gateway In WSS Queue and bid realtime events; cookie-authenticated handshake.

2.3 Runtime narrative

The console reaches a usable state in a fixed sequence:

  1. Boot. src/main.tsx mounts the React root, installs the Redux Provider, the i18n provider and the AuthProvider, then renders App.
  2. Session probe. AuthContext reads the non-sensitive profile from lib/auth.ts storage; an absent profile yields the unauthenticated state and route guards redirect to login.
  3. Route resolution. AppRoutes lazily loads the matched page behind ProtectedRoute and, where required, RoleGuard.
  4. Data hydration. RTK Query hooks fire; the request flows through baseQueryWithReauth with credentials: "include", so the httpOnly cookie accompanies every call.
  5. Realtime attach. On authenticated mount, useQueueSocket ensures a single Socket.IO connection, subscribes the active organization, and translates events into debounced cache invalidation.
  6. Failure paths. A 401 from REST or a 401 handshake refusal ends the session and clears local state (Section 4.3).

  • Test include. Vitest matches src/**/*.{test,spec}.?(c|m)[jt]s?(x).

@vitejs/plugin-react is the sole build plugin. There is no custom CSP injection plugin in this release; Content-Security-Policy and related HTTP security headers are a server/hosting responsibility and are recorded as deferred (C36).

4. Authentication and session management

4.1 Flow

Authentication is passwordless OTP. The console never stores a password and never receives or stores the JWT. The flow, as built:

  1. The user opens /login (Auth with initialStep="login") and submits a phone number. Auth calls requestLoginOtp() (src/services/auth.service.ts), a POST to /user/loginUser.
  2. The backend sends an OTP out of band. The console renders the OTP entry field (useOtpVerification, OTP_LENGTH = 6) with a 60-second (RESEND_COOLDOWN_SECONDS) resend cooldown; it auto-submits when six digits are complete.
  3. verifyOtp(phoneNumber, otp) POSTs to /user/verifyUserByOTP. On success the backend issues the session JWT as an httpOnly cookie (Section 4.2) and returns the non-secret userData.
  4. The client calls setAuth({ userData }) (AuthContext), which persists the profile and dispatches the Redux setAuth action; the socket is connected from the AuthContext effect.
  5. The user is navigated to the originally requested route (or /dashboard).
Open finding C3: role-omitted login contract vs. as-built body

src/utils/constant.ts:16-18 states, as a maintenance rule, that login and OTP verification send no roleId, leaving the backend to resolve the account's own role from UserRole. That is the contract we intended, and it is why the console can admit both role 11 and role 12. But the as-built requestLoginOtp and verifyOtp in src/services/auth.service.ts:19,27 still transmit roleId: QUEUE_ORG_ADMIN_ROLE (11), which contradicts their own docblock (lines 8-15) repeating the same role-omitted rule. Registration (registerUser) correctly sends 11, because provisioning is the role being created. We track the mismatch as C3, the only known client/contract mismatch; it doesn't weaken the session model, but it can reject a role-12 login if the backend honours the asserted role.

4.2 Where the session lives

The session credential is an httpOnly cookie named token, set by the backend (Utils/AuthCookie.js) when the OTP is verified. Because it is httpOnly, JavaScript (this console included) cannot read it. The client carries it automatically because every request is configured withCredentials/credentials: "include" (src/lib/api.ts:9-12, src/lib/redux/api/base.ts:38-41).

JavaScript storage holds only the non-secret profile, under queueadmin:user (src/lib/auth.ts). The record is { userData: { userId, userUniqueId, fullName, phoneNumber, email, roleId } } (StoredUser). A one-time migration (purgeLegacyAuth) rewrites any legacy queueadmin:auth record to the profile-only shape and removes the legacy keys (localStorage and sessionStorage); see C6.

Artifact Location Contains Readable by JS
Session JWT token httpOnly cookie Signed session claims No
User profile localStorage["queueadmin:user"] Non-secret profile only Yes
Queue selection localStorage["queueadmin:store"] (zustand persist) selectedOrgId only (partialized) Yes

4.3 Logout

Logout is centralised and defensive. AuthContext.logout() (src/context/AuthContext.tsx:38-44) walks three steps in order: disconnect the socket, fire a best-effort POST /user/logout to clear the server cookie, then clear local profile storage and dispatch the Redux logout action, which sets auth to null and always clears local storage (C9). Local state clears unconditionally even if the server call fails, so a network error cannot strand the user halfway through authentication.

Two additional paths end the session:

  • Global REST 401: baseQueryWithReauth (src/lib/redux/api/base.ts:61-67) intercepts any 401 and dispatches logout(); the axios transport does the same in src/lib/api.ts:15-26 (clear storage and redirect to /login). Because the auth slice is the single source of truth, every authed page unmounts at once (C7).
  • Socket 401 handshake: connect_error whose message contains “unauthorized” or “token” disconnects and ends the session via a dynamically-imported dispatch, avoiding an endless reconnect loop (C8, src/lib/socket.ts:168-178).

4.4 Guards

ProtectedRoute (src/components/auth/ProtectedRoute.tsx:16-60) requires a stored profile and, by default, at least one queue organization. It: redirects to /login when unauthenticated; withholds render while the organization list is loading; redirects to /setup-org when no organization exists; and fails open on a query error (lines 48-52) so a transient list error does not lock the user out. RoleGuard (src/components/auth/RoleGuard.tsx:14-27) admits the allow-list {11, 12, 3, 6} and redirects anything else to /login (C1, C2). Both guards are convenience layers; the backend is the authority (Section 13.3).

4.5 Session lifetime

Cookie and JWT lifetimes are role-based and server-set (Utils/SessionPolicy.js, Utils/AuthCookie.js): system admins (roles 3 and 6) get SESSION_TTL_ADMINS (default 24h); every other role, including queue org admins (11) and dispatchers (12), gets SESSION_TTL_OTHERS (default 365d). The cookie lifetime matches the JWT lifetime it carries. There is no refresh-token flow: an expiry surfaces as a 401, that triggers logout, and the user signs in again.

5.2 Guard stack and fail-closed behaviour

Protected routes compose two guards: ProtectedRoute (authentication + organization presence) on the outside, RoleGuard on the inside. The composition is fail-closed: an unauthenticated request is redirected to /login before any protected component mounts; an authenticated user without an organization is redirected to /setup-org; and a caller outside the role allow-list is redirected to /login (C1, C2). The single intentional permissive branch is the organization-query error path, which fails open to avoid a lock-out, and is not a security boundary.

6. State management

State is split by lifetime and sensitivity: a Redux store for session and server cache, and a small persisted zustand store for the active organization selection. There is no global state for form input; forms are local React state or react-hook-form.

6.1 Redux store shape

src/lib/redux/store.ts configures the store with three reducers, auth, queue and the RTK Query api reducer, and appends api.middleware for cache and tag orchestration.

Slice State Actions
auth { auth: StoredAuth | null; hydrated: boolean } hydrateAuth, setAuth, logout
queue { selectedOrgId: string | null; orgsCache: QueueOrganization[] | null } setSelectedOrgId, setOrgsCache, clearQueueState
api (RTK Query) Per-endpoint cache entries + tag registry Generated hooks; invalidated by tag

6.2 Slice behaviours that matter

  • Auth is the single source of truth. AuthContext reads state.auth.auth rather than owning state, so a 401 anywhere flips the UI to logged-out without a second source of truth (AuthContext.tsx:20-23). The slice initialises from getStoredAuth() so a reload rehydrates the profile synchronously. setAuth and logout in the slice also write/clear storage, keeping Redux and localStorage consistent (C6).
  • Queue slice is scratch state. selectedOrgId and orgsCache support UI selection; they are derived from URL/query data and can be cleared without data loss.

6.3 Persisted UI store (zustand)

src/store/queueAdminStore.ts is a persisted zustand store under the key queueadmin:store. Only selectedOrgId is persisted via partialize; socketConnected is intentionally transient. A one-time cleanup deletes a stale userCreatedOrgs key from an earlier schema. Selecting the active organization therefore survives reloads without persisting any server or secret data.

6.4 RTK Query API configuration

src/lib/redux/api/base.ts defines one API object with reducerPath: "api", refetchOnFocus: false, refetchOnReconnect: false and keepUnusedDataFor: 300 (seconds). Turning focus and reconnect refetch off lets the socket-driven invalidation of Section 8 drive freshness, which avoids redundant network churn. Nine tag types are registered: QueueOrganizations, QueueOrgMembers, QueueStatus, DriverQueue, DriverBids, DriverDirectory, Auth, VehicleTypes and ShipperRequests.

Endpoints are not declared on the base object; each feature module calls api.injectEndpoints(...) on the shared API, keeping features isolated while sharing one reducer/middleware. A stale comment at base.ts:92 says “now 22 total”; the as-built total is 28 endpoints across five modules (auth 3, queue-organization 11, driver-queue 9, shipper-request 3, vehicle 2). The comment is documentation debt only and is catalogued in Section 7.1.

7.2 Transport client

Two HTTP clients coexist. The RTK Query path uses fetchBaseQuery (src/lib/redux/api/base.ts:38-41) with baseUrl: getBaseUrl() and credentials: "include", wrapped by baseQueryWithReauth which converts any 401 into a global logout(). The service path uses a shared axios instance (src/lib/api.ts:9-26) with withCredentials: true and its own 401 interceptor (clear storage + redirect to /login). Both automatically carry the httpOnly cookie, so neither adds an Authorization header. The active OTP login uses the axios service path; feature screens use the RTK Query hooks.

getBaseUrl() (src/utils/baseUrl.ts) resolves the REST base as described in Section 3.4 and normalises it to end in /api.

7.3 Defensive payload handling

  • Vehicle types. useListVehicleTypesQuery is a queryFn that, on any error or malformed shape, registers and returns DEFAULT_VEHICLE_TYPES, so order creation is never blocked by missing reference data (C20, C31).
  • Explicit-id bid acceptance. useAcceptDriverRequestMutation validates each id against a UUID pattern and, when an id is missing, returns a visible CUSTOM_ERROR instead of guessing. The former heuristic (fetch 100 requests and fuzzy-match) was removed because under concurrent bidding it could resolve to the wrong driver with no error (C18).
  • Formatters. src/utils/formatters.ts and the order mappers decode optional fields defensively so a single malformed record degrades one row rather than crashing a list.

7.4 Idempotency and cache notes

Mutations invalidate by tag rather than patching cache entries (C22). List reads are deliberately bounded to keep payloads predictable: queue organizations and shipper requests use limit=100; batches use limit=100 with includeBids; the driver directory uses limit=20 (C35). There is no endpoint retry/backoff layer beyond the socket reconnection policy (Section 8.4).

8. Realtime integration

8.1 Socket lifecycle

src/lib/socket.ts owns a single module-scoped Socket.IO connection. It is created by connectSocket() (called from the AuthContext effect when an authenticated profile exists) and torn down by disconnectSocket() on logout. Connection options: transports ["websocket", "polling"], withCredentials: true, auth carrying { user, phoneNumber }, reconnection enabled with 5 attempts, 1.5s–5s backoff, and a 20s timeout (C5, C8).

The socket identity is computed by extractCredentials(): roles 3 and 6 map to "admin"; every other role, including queue org admin (11) and dispatcher (12), maps to "queueOrgAdmin". Role 12 is deliberately not given its own identity: the backend keys sockets as ${userType}:${phone} and queue fan-out selects roleId IN (11,12) under the queueOrgAdmin key, so a distinct dispatcher identity would silently receive no events (C24).

8.2 Event routing

Inbound payloads are handled by handleQueuePayload(), which tolerates both JSON strings and objects, extracts a message type from messageTypes (string or { type, message }) or the message field, and ignores acknowledgements and heartbeats (subscribed, unsubscribed, ping, pong). Non-acknowledgement events are forwarded to registered handlers (onQueueEvent) and simultaneously trigger a debounced cache invalidation (C23).

Signal Classification Invalidation (debounced)
queue_org_approved, queue_org_updated, queue_org_deleted, queue_member_added, org_approved, or a payload with org id + approval status Organization event QueueOrganizations after 100 ms.
Any other queue/bid event Operational event QueueStatus, DriverQueue, ShipperRequests after 250 ms.

The debounce collapses bursts into one invalidation, and a parse failure still triggers an invalidation so the cache cannot drift permanently stale (C23).

8.3 Subscription model

Subscriptions are refcounted in a module-scoped Map keyed ${queueOrganizationUniqueId}_${queueDate||""}. subscribeToQueue() increments the refcount (and connects if needed); unsubscribeFromQueue() decrements and only emits queue:unsubscribe when the count reaches zero (C24). On every (re)connect the handler replays all active subscriptions with queue:subscribe, so a transient network blip does not silently unsubscribe the page (src/lib/socket.ts:156-161).

8.4 Connection state and revocation

Connectivity is mirrored into the zustand store via setSocketConnected and surfaced by useQueueSocket as { socketConnected, isLive }. A connect_error whose message contains “unauthorized” or “token” disconnects and dispatches the Redux logout, ending the session rather than retrying indefinitely (C8, src/lib/socket.ts:168-178). The dynamic imports of the store and slice (clearSessionOnUnauthorizedSocket) avoid a module cycle.

9. Feature-level LLD

This section takes each requirement family from the companion SRS/SDD down to the components, handlers and schemas that implement it: FR-AUTH, FR-ROLE/ACCESS, FR-ORG, FR-QUEUE, FR-BID, FR-ORDER, FR-REALTIME and FR-REPORT, with the cross-cutting NFR-SEC and NFR-DEPLOY families realised as the numbered controls of Section 15.

9.1 Authentication (FR-AUTH)

Authentication is phone-first and passwordless. Shared inputs live in fields.tsx; the six-box one-time-code entry is OtpDigitInputs.tsx.

10. Data model and persistence

10.1 Client-side domain types

Domain shapes are declared once in src/types/queue.ts (roles, organisation types QUEUE_ORG_TYPES, journey status, queue and member records) and consumed by the RTK Query layer. Organisations, queues, members, bids, shipper requests and vehicle types are held by the backend service. The client keeps them only as in-memory RTK Query caches (Section 10.4) and re-reads them from the server; it never treats a cached copy as authoritative (C30).

The API slice (src/lib/redux/api/base.ts) defines nine cache tags: QueueOrganizations, QueueOrgMembers, QueueStatus, DriverQueue, DriverBids, DriverDirectory, Auth, VehicleTypes and ShipperRequests. Mutations invalidate the tags they affect, and realtime events invalidate the same tags through the debounced path of Section 8.2, so the cache converges on the server's view rather than on pushed payloads (C23, C30).

11.2 Organisation approval status

Organisations carry an approval state rendered by components/queue-org-manage/StatusBadge.tsx and acted on by AdminApprovalActions.tsx (approve via queueOrganization/:id/approve). 11.3 Session states

The auth Redux slice exposes { auth, hydrated }. States are: anonymous (no profile; routing redirects to /login), hydrating (profile being restored from storage before guards decide), authenticated (profile present, socket connected) and expired (a 401 clears the profile and returns the user to /login). The hydration gate prevents a flash of protected content before the guard decision (C14, C31).

11.4 Realtime connection state

Socket connectivity is mirrored into the zustand store and surfaced by useQueueSocket as { socketConnected, isLive }. A connect_error whose message indicates an unauthorised or token failure ends the session rather than retrying indefinitely (C8, Section 8.4).

11.5 Known gaps, assumptions and limitations

We record the behaviours below so reviewers can tell them apart from the secured paths above. Each one maps to an open finding in Section 15.3.

  • Settings are display-only. Profile save, push/email/2FA and account deletion are presented but not persisted; save attempts are refused with an explicit message rather than silently faked (C28, F4).
  • Check-in is not geofenced. A modelled checkinRadiusKm value is not enforced as a physical gate; only the driver id and optional queue number are validated (C16, F7).
  • Auth roleId. Login/OTP/register transmit roleId: 11 although the API contract comment states no role should be sent (C3, F1).
  • Host-level controls. TLS/HSTS, CSP and other response security headers are a hosting/server responsibility and are not asserted by the repository (C25, F5).
  • No token refresh. Session expiry forces re-authentication; there is no silent refresh (C14, F6).

12.2 Input sanitisation and output encoding

Text and email inputs are sanitised in the schema layer by stripTags, stripCtrl, sanitizeText and sanitizeEmail, which remove HTML tags and control characters, collapse whitespace and normalise email (src/schemas/queue.ts:7-17). Rendering relies on React's automatic output escaping; the codebase contains no dangerouslySetInnerHTML, innerHTML or eval usage (C17, C18). Together these close the stored/reflected XSS vector of Annex A#4.

12.3 Phone normalisation

utils/phoneFormatter.ts strips a leading +251, 251 or 0, caps input at nine digits, renders the X-XX-XX-XX-XX mask and produces E.164 +251… for transmission. isValidPhoneDigits accepts exactly nine digits (C19).

12.4 Error handling

API errors are normalised by getApiError (lib/api.ts) and parseError (utils/parseError.ts) into a safe message that is shown as a toast via sonner (<Toaster richColors /> in main.tsx). Raw server stack traces, SQL or internal identifiers are never surfaced to the user. A 401 from any request routes through the interceptor to clearAuth() and a redirect to /login, unless the user is already on the login page (C14, C35).

12.5 Logging and build artefacts

The production bundle is built with source maps disabled (vite.config.ts), so client code is not shipped in readable form, and no token or credential is written to logs (C29, C35). Application monitoring, audit logging and log retention are server-side responsibilities (NFR-DEPLOY, C25); the client's only diagnostic surface is the transient toast described above.

13. Security implementation

13.1 Trust boundaries

The client is an untrusted rendering surface. Every privilege decision that matters is made by the backend service; the browser-side guards and role allow-lists exist for usability and defence in depth. Figure 2.1 (Section 2) shows the boundary between the SPA, the API and the Socket.IO channel, all of which authenticate with the same session cookie. This is the design's response to Annex A#8 (lack of authentication and authorisation) and Annex B tests 23–28.

13.2 Cross-site scripting (XSS)

All rendering flows through React's escaped JSX, and no unescaped-HTML sink is used (C18). User-supplied text is additionally stripped of tags and control characters at the schema boundary (C17). No user content is injected into URLs or attribute positions without encoding, addressing Annex A#4.

13.3 Authentication and session management

Authentication is phone + one-time code; the session is a backend-issued httpOnly cookie set at verifyUserByOTP. JavaScript never receives, stores or transmits a bearer token; the only persisted auth value is the non-sensitive profile, and the legacy token key is actively purged (C11, C12). Requests carry cookies via credentials: "include"; there is no Authorization header. A 401 or an unauthorised socket error ends the session immediately (C8, C14), and logout performs a best-effort server call before clearing local state (C15). This addresses Annex A#3 (improper session management) and Annex B tests 63–77.

13.4 Cross-site request forgery (CSRF)

Because the session is cookie-based, CSRF protection depends on the cookie's SameSite attribute and the backend's cross-origin policy, both of which are server-side settings (C25, F5); the client sends no bespoke CSRF token. This dependency is recorded rather than claimed as a client control (Annex A#5).

13.5 Transport security

The canonical origin is HTTPS (index.html canonical and Open Graph URLs, plus public/sitemap.xml), and the API base resolves to an absolute /api URL by baseUrl.ts (C21). There is no client-side use of http:// resources and no mixed content (C22). The validity and renewal of the TLS certificate, and the presence of HSTS, are hosting obligations (C25, Annex B#14–18).

13.6 Information disclosure

public/robots.txt allows the public site and points only at sitemap.xml; it lists no sensitive paths (C26). The client bundle carries only VITE_-prefixed public variables and no secrets (C27), and production builds are shipped without source maps (C29). There are no shipped debug routes or developer panels beyond the intentional /security self-assessment page (C35).

13.7 Supply chain and dependency hygiene

Dependencies are declared with pinned lockfile resolution and no runtime CDN imports; the build is fully local (C33). Runtime dependencies are limited to the React/Redux/RTK Query, routing, forms, validation, socket, i18n and chart-free UI stack listed in package.json. An unused @tanstack/react-query dependency remains in the manifest (F3).

13.8 Control summary

Every implementation decision above is carried as a numbered control C1–C36 in the register of Section 15.1, mapped to the file and symbol that provides the evidence. Open items and server-side dependencies are listed in Section 15.3.

16. Deployment and operations

16.1 Build and release

The release artefact is a static bundle produced by npm run build (tsc -b && vite build) on Node ≥ 20.19.0. Vite emits hashed, minified assets to dist/, splits vendor/redux/icon chunks (vite.config.ts) and disables source maps in production (C29). The INSA document set is rendered to PDF with the same sources as the master: node scripts/render-pdf.cjs --all renders every docs/insa/*.html and audits each PDF for page count and horizontal padding (C36).

16.2 Configuration

Runtime configuration is limited to public VITE_ variables resolved at build time by lib/baseUrl.ts, in priority order: VITE_API_BASE_URL → VITE_API_URL → /api, normalised to end in /api. No secret is provided to the client build (C27). The dev server proxies /api and the Socket.IO upgrade path only when VITE_API_BASE_URL is set (C34).

16.3 Hosting and transport

The console is served as a single-page application under the canonical HTTPS origin https://queue.dynamicsroute.tech/. The host is responsible for TLS termination, certificate renewal, HSTS, security headers, the cookie's Secure/HttpOnly attributes and the SPA fallback route; these are the server-side dependencies recorded in C25 and finding F5.

16.4 Operations, monitoring and disclosure

Application monitoring, audit logging, rate limiting on authentication and e-mail, and incident response are backend responsibilities (NFR-DEPLOY, C25). On the client side, public/robots.txt and public/sitemap.xml expose only the public root (C26), and no operational endpoints or debug surfaces are shipped (C35).

16.5 Business continuity and change control

Backups, disaster recovery and continuity are owned by the hosting provider. Changes to the client follow the build gates of Section 14.2 and the environment separation of Section 16.2; the repository commits no secrets and ignores local environment files (C34). Significant changes are expected to pass an operational risk assessment before release (2.5 OPM-J), which is a process rather than a code control and is therefore recorded here rather than in the register.
