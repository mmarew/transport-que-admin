1. Introduction

1.1 Purpose

This is the security documentation for Dynamics Queue Admin (queadmin-frontend), the dispatch-queue management console used by queue staff to manage driver queues, shipper requests, trips, queue organizations and real-time dispatch operations. It is submitted to the Information Network Security Agency (INSA) in support of the Secure Website Management Standard, 2014 EC. The document states the security requirements the asset is designed to meet, the controls actually implemented in the submitted release, the evidence for those controls, and — with equal prominence — the controls that are planned, outstanding, organizational, or owned by a separate system.

1.2 Scope

In scope: the client-side single-page application in this repository (React 19 + TypeScript + Vite 8), its production build, and its client-side security behaviours: session handling, route guards, form validation and sanitisation, storage handling, and error handling. The application is served at queue.dynamicsroute.tech.

Out of scope: the backend system of record (transportBackEndNative, Node.js/Express + MySQL), the driver mobile application, the shipper application, and the hosting platform itself. The backend is the enforcement boundary for authentication, authorization, session lifetime, upload handling and request validation; those obligations are identified here as dependencies and must be evidenced by the backend's own submission. The hosting platform (web server, TLS termination, certificate management, HTTP response headers) is a separate hosting engagement. This repository contains no server configuration, no Content-Security-Policy and no security response headers; the document states this plainly rather than implying a server layer that does not exist in the source.

1.3 Governing standard

The governing standard is the INSA Secure Website Management Standard, 2014 EC. It defines five focus areas — Requirement Gathering and Analysis (2.1), Design (2.2), Implementation (2.3), Hosting (2.4), and Operation and Management (2.5) — plus Annex A (eight common vulnerabilities and threats) and Annex B (a 102-item minimum security testing checklist). This document addresses all five focus areas and both annexes in turn.

1.4 Summary of outcome

The application layer is in reasonable shape. The console uses an httpOnly-cookie session model and never reads or stores a JWT in JavaScript (getToken() in src/lib/auth.ts deliberately returns null); login is one-time-password only, so there are no passwords to leak; forms are validated and sanitised with React Hook Form and Zod (src/schemas/queue.ts strips HTML tags and control characters); the client never renders untrusted HTML (a source scan found no dangerouslySetInnerHTML, innerHTML, eval or new Function in src/); logout clears the stored session profile and calls the backend logout; a global 401 handler ends the session on any unauthorized response; and production sourcemaps are disabled.

The largest gaps are real and are stated without mitigation. There is no Content-Security-Policy and no security response header anywhere in the repository, and no server configuration to deliver them, so anti-clickjacking, HSTS, anti-sniffing and related items cannot be evidenced from this asset. The error utility src/utils/parseError.ts logs the raw error object by default (console.error("[parseError]", error)) and is not gated to development builds, so failure payloads can reach the browser console in production. The OTP is submitted to the backend as a JavaScript Number, which corrupts codes with a leading zero. The client also sends roleId and statusId on login and OTP verification even though the code comments and README claim it does not, so the backend must be confirmed to ignore them. There is no continuous integration, no dependency audit gate and no security linting plugin. Sections 14 and 16 quantify all of this precisely.

3. System description

3.1 Architecture

Dynamics Queue Admin is a standalone single-page application. It is loaded once from the static host, then communicates with a single backend over HTTPS (REST/JSON) and a single real-time channel (Socket.IO, with cookie credentials). It also calls third-party services directly from the browser for fonts, avatars and place search. The console is a queue-operations tool: queue organizations manage their driver queues, check drivers in, dispatch vehicles against shipper requests, and receive live queue updates. It holds no server-side logic and stores no database of its own; all state of record lives in the backend.

5. Authentication and session management

5.1 Authentication flow

  1. The user enters a phone number; the console requests an OTP (requestLoginOtp, POST /user/loginUser).
  2. A one-time password is delivered by SMS; the console collects six digits and verifies it (verifyOtp, POST /user/verifyUserByOTP).
  3. On success the backend issues a session JWT in an httpOnly cookie. The console does not read or store the token: the RTK Query onQueryStarted handler stores only userData (src/lib/redux/api/authEndpoints.ts).
  4. The console persists only the non-sensitive profile in localStorage under queueadmin:user so the UI can render the user's name and role across reloads (src/lib/auth.ts).
Implemented application-layer controls (verified in source)
  • No JS-readable token. getToken() returns null by design; the lexically stored record is { userData } only. Saved under queueadmin:user; the legacy queueadmin:auth record that could have held a token is migrated and then deleted (purgeLegacyAuth()).
  • Cookie-credential requests. Both the axios layer (src/lib/api.ts, withCredentials: true) and the RTK Query base (src/lib/redux/api/base.ts, credentials: "include") send the session cookie. No Authorization header is constructed.
  • Logout clears state. AuthContext.logout() disconnects the socket, calls POST /user/logout (best-effort, to clear the httpOnly cookie server-side), clears the stored profile via clearAuth(), and dispatches the redux logout action — Annex B #39, #63.
  • Central 401 handling. Any 401 on any API call ends the session: the axios interceptor clears auth and redirects to /login, and baseQueryWithReauth dispatches logout(). A 401 on the socket handshake also ends the session so the client does not reconnect-loop against a dead cookie (src/lib/socket.ts).
  • Phone masking. The OTP screen shows a masked number (maskedPhone in src/hooks/useOtpVerification.ts).
Findings that prevent Pass status (verified in source)
  • OTP transmitted as a number. verifyOtp sends OTP: Number(OTP) (src/services/auth.service.ts). A six-digit code with a leading zero is transmitted with the zero stripped, so a valid code can be rejected (and the behaviour differs from the string-safe handling expected). Annex B #26 is marked Open on this ground.
  • roleId/statusId sent despite contrary comments. Both requestLoginOtp and verifyOtp send roleId: QUEUE_ORG_ADMIN_ROLE (11) and statusId: 1, while the in-file comment and the README state that the client does not send a role. The backend must be confirmed to derive the role from the session and ignore these client-supplied values. Annex B #28, #36.
  • Raw error logging. parseError logs the entire error object unless silent is passed, and it is not gated to development builds (src/utils/parseError.ts:116). This is discussed in §9 and is the basis for marking the token/log-disclosure items Open.
  • Server messages surfaced. resolveServerMsg returns the backend's message/error text when present, so a failed OTP can display backend prose that may distinguish "unknown user" from "wrong code" (username enumeration). Annex B #35 is Open.

5.2 Session lifetime

Session lifetime is backend-controlled and not visible to the client. VITE_JWT_EXPIRATION_DAYS=7 exists in .env.development / .env.example but is read nowhere in src/; it is misleading and should be removed. Per the backend session policy documentation (README, referencing Utils/SessionPolicy.js), sessions are role-dependent: Admin (3) and SuperAdmin (6) = 24 hours; Queue Org Admin (11) and Queue Dispatcher (12) = 365 days. The 365-day lifetime for queue staff is unusually long and is called out as a hardening recommendation (§17). A periodic-expiration requirement (Annex B #76) therefore rests entirely on the backend.

6. Authorization and access control

6.1 Role model

The console is intended for queue-console roles: Queue Org Admin (role 11), Queue Dispatcher (role 12), platform Admin (role 3) and Super Admin (role 6). The role is part of the stored profile and is resolved by the backend at login. Membership in a specific queue organization is a backend relationship; the client cannot grant it.

6.2 Client route-boundary guards

Two components wrap protected routes and run before the child renders:

  • src/components/auth/RoleGuard.tsx — the user must hold one of the allowed role IDs ({ 11, 12, 3, 6 }), otherwise the guard redirects to /login. Roles 3 and 6 are included because they are legitimate platform operators of the queue console.
  • src/components/auth/ProtectedRoute.tsx — the user must be authenticated and must have at least one queue organization, otherwise they are redirected to /setup-org. It waits for the organization query to settle before deciding.
Fail-open behaviour in ProtectedRoute (Annex B #32)

When the organization query returns an error, ProtectedRoute returns true for hasOrg and allows the user through: orgsError ? true : false (src/components/auth/ProtectedRoute.tsx:48-52). This is a deliberate availability choice — a transient backend failure should not lock operators out of a live queue — but it is a fail-open condition and is marked Open under Annex B #32. It does not bypass authentication (the session check precedes it) nor backend authorization; it only affects the client's organization-setup gate. The recommended remediation is to distinguish an authorization failure (redirect) from a transport failure (show a retryable error, not the app).

The backend is the enforcement boundary — explicit statement

The route guards are a UI safety control, not an authorization boundary. A user who forges their stored profile or calls the API directly must still be denied by the backend. The backend must:

  • derive roleId/statusId from the session, never from the request body (the client sends them for legacy reasons — see §5.1);
  • scope every queue-organization query and mutation to the cookie identity;
  • authorize every organization and queue identifier against the session's memberships.

Until the backend team evidences these, Annex B #23, #24, #27 and #28 cannot be closed.

6.3 Per-action checks

Individual actions present only the affordances the role permits (for example, bid approval is shown only to role 11 in the bidding board), and every mutating request is sent to the backend, which is solely responsible for accepting or rejecting it. No client-side decision is treated as authoritative.

6.4 Privilege categories and lifecycle

The code implements privilege categorization (INSA 2.5.D) through the role set above and the queue-organization membership model. Granting and revoking access, and rotating credentials on a fixed schedule, are organizational procedures that are not evidenced in this repository (INSA 2.5.C and 2.5.E).

7. Transport security

7.1 HTTPS

The production URL is HTTPS-only (queue.dynamicsroute.tech). The application is configured to call the API over https:// in development (VITE_API_BASE_URL=https://dev.dynamicsroute.tech) and defaults to the same-origin /api path in a production build, which inherits the page's TLS. The socket client targets the same host and sends the cookie with withCredentials: true.

Not independently verified for this submission

This repository contains no server configuration, so the HTTP→HTTPS redirect, the TLS protocol/cipher set, and the certificate chain on the production host were not independently assessed here. The application itself only ever addresses HTTPS origins in production. Annex B #13 and #15 are marked Pass on the basis of the application's own transport choices (HTTPS/WSS and no mixed content); #14 is marked Pass with the platform redirect noted as unverified; #16 (HSTS) and #17–#18 (TLS/certificate) are Open.

7.2 Socket transport

src/lib/socket.ts initializes Socket.IO with transports: ["websocket", "polling"], withCredentials: true, reconnectionAttempts: 5, reconnectionDelay: 1500, reconnectionDelayMax: 5000 and timeout: 20000. The polling fallback is retained for restrictive networks; unlike a purely WebSocket-pinned client, the polling handshake is an HTTP request that must also be protected by the platform's cookie and CSRF controls.

7.3 HSTS and cookie scope

No Strict-Transport-Security header is defined anywhere in the repository, so HSTS is absent (Annex B #16). Because a production build defaults to a same-origin API path, the session cookie may be same-site; if the deployment instead splits the SPA and API across registrable domains, the cookie must be SameSite=None; Secure and CSRF defence cannot rely on the default SameSite=Lax (see §5.3 and §14 #61, #62). This ambiguity must be resolved by the deployment and the backend before submission.

8. Application security controls

8.1 Content-Security-Policy

There is no CSP — stated plainly

A full-repository scan (src/, public/, index.html, vite.config.ts) found no Content-Security-Policy — no meta tag, no build-time injection, and no server configuration to deliver a header. Unlike a hardened SPA, this asset provides no script-execution policy to the browser. Annex B #83 (non-specific content types), #85 (anti-sniffing) and #96 (anti-clickjacking) are therefore Open, and there is no defence-in-depth layer behind React's output encoding for Annex B #43.

Note that index.html embeds an inline <script type="application/ld+json"> structured-data block. A strict script-src policy introduced later would need to accommodate it with a hash or nonce, or the block should be moved to an external file. This is recorded as a dependency of the remediation in §17.

8.2 Security response headers

No security response headers are configured in this repository: X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy are all absent. The hosting platform may add some of these, but that is outside this asset and is not evidenced. They are recorded as hosting items in §16.

8.3 Client-side output encoding

  • React escaping. All untrusted values are rendered through JSX text nodes and attribute bindings, which React escapes by default (Annex B #43).
  • No raw HTML sinks. A source scan found no dangerouslySetInnerHTML, innerHTML, eval, new Function or document.write in src/.
  • Input sanitisation. Zod transforms strip HTML tags and control characters from names, addresses and emails before they are stored or sent (src/schemas/queue.ts: stripTags, stripCtrl, sanitizeText, sanitizeEmail).

Without a CSP, these controls are the only layer preventing script injection; the recommendation in §17 is to add a policy as the first server-side change.

8.4 Build hardening

  • Sourcemap suppression. vite.config.ts sets build.sourcemap = process.env.NODE_ENV !== "production", so development builds carry sourcemaps and production builds do not. This is effective but implicit; pinning an explicit false for production is recommended (Annex B #6).
  • No secrets in the bundle. Only public configuration (API/socket hosts) is referenced from environment variables; no API keys or credentials are embedded or committed.

9. Input validation and data handling

9.1 Form validation and sanitisers

Forms use react-hook-form with zod schemas (src/schemas/queue.ts): login, registration, organization setup, check-in and dispatch. Schemas constrain length and format, and transform values to strip HTML tags (stripTags), remove non-printable control characters (stripCtrl), collapse whitespace (sanitizeText) and normalise email (sanitizeEmail). Phone numbers are normalised to E.164 (+251…) by src/utils/phoneFormatter.ts and src/lib/authConfig.ts. Client validation is a usability and hygiene control only; the backend must re-validate every field.

9.2 File uploads

No file upload feature

The console does not upload or download files: a source scan found no FormData, file input, FileReader or multipart request. The Annex B File Upload group (#78–#82) is therefore marked N/A for this asset. If uploads are added later (for example, compliance documents), the validation and storage controls must be designed and added to this document.

9.3 Production error handling and log hygiene

Finding: raw error logging is not dev-gated

src/utils/parseError.ts runs console.error("[parseError]", error) unless the caller passes { silent: true }. It is not gated behind import.meta.env.DEV. The logged error object can include the request configuration and response data (which for auth calls can carry the phone number and OTP). This is a production information-disclosure and log-hygiene gap, and it is the reason Annex B #4 (sensitive information in logs/errors) and #77 (disclosure of tokens in logs) are marked Open, and it also contributes to #7.

The user-facing path is better: parseError returns mapped, generic messages for HTTP statuses (401 → "Session expired", 403 → "You do not have permission", etc.). However, when the backend supplies a message/error string it is surfaced to the user (resolveServerMsg), which can disclose internal detail. Consider returning only server messages from an allow-list.

9.4 Client-side data and PII handling

The session JWT lives only in the httpOnly cookie; localStorage holds the non-secret profile (queueadmin:user: name, phone, email, role) used for rendering. On logout, clearAuth() removes that profile from both localStorage and sessionStorage. Other local keys (app_language, queueadmin:store — a UI selection only, insa_security_checklist_v1, theme and sidebar preferences) hold no personal data and are not cleared; this is acceptable but is noted for completeness. The residual risk is that the profile is stored in cleartext while signed in; this is a deliberate routing decision and is recorded in §16.

11. Dependency and supply-chain management

11.1 Dependency auditing

npm audit --omit=dev reports one high-severity vulnerable runtime dependency. The remediation is a one-command fix (npm audit fix) but is not yet applied and is not enforced anywhere. This fails Annex B #90 (missing security updates).

Package Range Severity Notable advisories
axios 1.0.0 – 1.19.0 High Prototype-pollution gadgets (fetch adapter, default instance, toFormData options), ReDoS in the data: URL parser, redirect-based SSRF, HTTP/2 adapter DNS/proxy bypass, and header injection via inherited headers (12+ advisories)

11.2 Static analysis and security linting

The ESLint configuration (eslint.config.mjs) uses @eslint/js, typescript-eslint, eslint-plugin-react and eslint-plugin-react-hooks only. There is no security plugin (no eslint-plugin-security), so risky patterns such as non-literal regular expressions, timing comparisons or unsafe object injection are not flagged. oxlint is installed and configured but is not a security gate. The lint script is eslint . --ext ts,tsx --max-warnings 0, while the README describes npm run lint as oxlint — the documentation and the script disagree.

11.3 A gap: unused and mis-declared dependencies

  • @tanstack/react-query is listed in package.json but nothing imports it; the project uses RTK Query. It is dead weight and expands the attack surface and audit scope for no benefit.
  • .npmrc sets legacy-peer-deps=true, which suppresses peer dependency resolution and weakens reproducibility of the install graph.

11.4 Continuous integration

No CI today

There is no .github/ directory, no Dependabot configuration, no secret scanning and no build pipeline. Nothing catches dependency drift, ensures a clean rebuild on deploy, or runs the test suite (107 tests, all passing) automatically. A recommended workflow is given in §17.

12. Deployment and hosting security

12.1 Deployment model

The console is built to a static bundle (npm run build: tsc -b && vite build) and served from a document root (dist/). The production host serves a static site and terminates TLS. The development server proxies /api and /socket.io to the backend (vite.config.ts).

12.2 Server configuration status

17. Security recommendations and roadmap

The remediation is phased by risk reduction per unit effort. Phases 1–4 are code-only and independent of the platform decision; Phase 0 and Phase 6 require hosting or backend action and are the highest-impact changes. The recommended order is Phase 1 → Phase 2 → Phase 3 → Phase 4, with Phase 0 started immediately in parallel.

Phase 0 — Server/header layer (highest impact; needs hosting access)

Deliver a CSP and security-header layer on queue.dynamicsroute.tech. The policy must account for the inline JSON-LD block in index.html (hash or nonce, or move the block to an external file). Recommended header set: Content-Security-Policy (with frame-ancestors 'none'), Strict-Transport-Security, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, Permissions-Policy, COOP/CORP, a Cache-Control policy (no-store on HTML, immutable on hashed assets), method restriction, and 404 blocks for /.env, /.git and *.map.
