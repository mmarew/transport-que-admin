1. Introduction

1.1 Purpose

This is the security documentation for Dynamics Queue Admin (queadmin-frontend), the dispatch-queue management console used by queue staff to manage driver queues, shipper requests, trips, queue organizations and real-time dispatch operations. It is submitted to the Information Network Security Agency (INSA) in support of the Secure Website Management Standard, 2014 EC. The document states the security requirements the asset has to meet, the controls actually implemented in the submitted release, the evidence for those controls, and, with equal prominence, the controls that are planned, outstanding, organizational, or owned by a separate system.

1.2 Scope

In scope: the client-side single-page application in this repository (React 19 + TypeScript + Vite 8), its production build, and its client-side security behaviours: session handling, route guards, form validation and sanitisation, storage handling, and error handling. The application is served at queue.dynamicsroute.tech.

Out of scope: the backend system of record (transportBackEndNative, Node.js/Express + MySQL), the driver mobile application, the shipper application, and the hosting platform itself. The backend is the enforcement boundary for authentication, authorization, session lifetime, upload handling and request validation; those obligations are identified here as dependencies and must be evidenced by the backend's own submission. The hosting platform (web server, TLS termination, certificate management, HTTP response headers) is a separate hosting engagement. This repository contains no server configuration, no Content-Security-Policy and no security response headers; the document states this plainly rather than implying a server layer that does not exist in the source.

1.3 Governing standard

The governing standard is the INSA Secure Website Management Standard, 2014 EC. It sets out five focus areas: Requirement Gathering and Analysis (2.1), Design (2.2), Implementation (2.3), Hosting (2.4), and Operation and Management (2.5), along with Annex A (eight common vulnerabilities and threats) and Annex B (a 102-item minimum security testing checklist). This document addresses all five focus areas and both annexes in turn.

1.4 Summary of outcome

The application layer is in reasonable shape. The console uses an httpOnly-cookie session model and never reads or stores a JWT in JavaScript (getToken() in src/lib/auth.ts returns null by design); login is one-time-password only, so there are no passwords to leak; forms are validated and sanitised with React Hook Form and Zod (src/schemas/queue.ts strips HTML tags and control characters); the client never renders untrusted HTML (a source scan found no dangerouslySetInnerHTML, innerHTML, eval or new Function in src/); logout clears the stored session profile and calls the backend logout; a global 401 handler ends the session on any unauthorized response; and production sourcemaps are disabled.

The largest gaps are real and are stated plainly. There is no Content-Security-Policy and no security response header anywhere in the repository, and no server configuration to deliver them, so anti-clickjacking, HSTS, anti-sniffing and related items cannot be evidenced from this asset. The error utility src/utils/parseError.ts logs the raw error object by default (console.error("[parseError]", error)) and is not gated to development builds, so failure payloads can reach the browser console in production. The OTP is submitted to the backend as a JavaScript Number, which corrupts codes with a leading zero. The client also sends roleId and statusId on login and OTP verification even though the code comments and README claim it does not, so the backend must be confirmed to ignore them. There is no continuous integration, no dependency audit gate and no security linting plugin. Sections 14 and 16 quantify all of this.

3. System description

3.1 Architecture

Dynamics Queue Admin is a standalone single-page application. It is loaded once from the static host, then communicates with a single backend over HTTPS (REST/JSON) and a single real-time channel (Socket.IO, with cookie credentials). It also calls third-party services directly from the browser for fonts, avatars and place search. The console is a queue-operations tool: queue organizations manage their driver queues, check drivers in, dispatch vehicles against shipper requests, and receive live queue updates. It holds no server-side logic and stores no database of its own; all state of record lives in the backend.

5. Authentication and session management

5.1 Authentication flow

  1. The user types a phone number and the console asks the backend for an OTP (requestLoginOtp, POST /user/loginUser).
  2. A one-time password arrives by SMS. The console takes the six digits and verifies them (verifyOtp, POST /user/verifyUserByOTP).
  3. On success the backend issues a session JWT in an httpOnly cookie. The console never reads or stores the token; the RTK Query onQueryStarted handler keeps only userData (src/lib/redux/api/authEndpoints.ts).
  4. The console saves just the non-sensitive profile to localStorage under queueadmin:user, so the UI can show the user's name and role across reloads (src/lib/auth.ts).
Implemented application-layer controls (verified in source)
  • No JS-readable token. getToken() returns null by design, and the record that is stored is { userData } and nothing else. It is saved under queueadmin:user; the older queueadmin:auth record, which could have held a token, is migrated and then deleted (purgeLegacyAuth()).
  • Cookie-credential requests. The axios layer (src/lib/api.ts, withCredentials: true) and the RTK Query base (src/lib/redux/api/base.ts, credentials: "include") both send the session cookie. No Authorization header is ever built.
  • Logout clears state. AuthContext.logout() drops the socket, calls POST /user/logout on a best-effort basis to clear the httpOnly cookie server-side, removes the stored profile with clearAuth(), and dispatches the redux logout action (Annex B #39, #63).
  • Central 401 handling. Any 401 on any API call ends the session: the axios interceptor clears auth and redirects to /login, and baseQueryWithReauth dispatches logout(). A 401 during the socket handshake ends the session as well, so the client does not reconnect-loop against a dead cookie (src/lib/socket.ts).
  • Phone masking. The OTP screen shows a masked number (maskedPhone in src/hooks/useOtpVerification.ts).
Findings that prevent Pass status (verified in source)
  • OTP transmitted as a number. verifyOtp sends OTP: Number(OTP) (src/services/auth.service.ts). A six-digit code that starts with a zero loses that zero in transit, so a valid code can be rejected, and the behaviour differs from the string-safe handling that was expected. Annex B #26 is marked Open on this ground.
  • roleId/statusId sent despite contrary comments. Both requestLoginOtp and verifyOtp send roleId: QUEUE_ORG_ADMIN_ROLE (11) and statusId: 1, yet the in-file comment and the README say the client does not send a role. The backend has to be confirmed to take the role from the session and ignore these client-supplied values. Annex B #28, #36.
  • Raw error logging. parseError logs the whole error object unless the caller passes silent, and it is not gated to development builds (src/utils/parseError.ts:116). This is discussed in §9, and it is why the token and log-disclosure items are marked Open.
  • Server messages surfaced. resolveServerMsg returns the backend's message/error text when it is present, so a failed OTP can display backend prose that tells "unknown user" apart from "wrong code", which is username enumeration. Annex B #35 is Open.

5.2 Session lifetime

Session lifetime is set by the backend and not visible to the client. VITE_JWT_EXPIRATION_DAYS=7 appears in .env.development and .env.example, but nothing in src/ reads it; it is misleading and should be deleted. The backend session policy documentation (README, referring to Utils/SessionPolicy.js) makes lifetimes role-dependent: Admin (3) and SuperAdmin (6) = 24 hours; Queue Org Admin (11) and Queue Dispatcher (12) = 365 days. The 365-day lifetime for queue staff is unusually long and appears as a hardening recommendation in §17. The periodic-expiration requirement (Annex B #76) therefore rests entirely on the backend.

6. Authorization and access control

6.1 Role model

The console serves a small set of queue-console roles: Queue Org Admin (role 11), Queue Dispatcher (role 12), platform Admin (role 3) and Super Admin (role 6). The role is stored in the profile and resolved by the backend at login. Being a member of a particular queue organization is a backend relationship, and the client cannot grant it.

6.2 Client route-boundary guards

Two components wrap the protected routes and run before the child renders:

  • src/components/auth/RoleGuard.tsx checks that the user holds one of the allowed role IDs ({ 11, 12, 3, 6 }); if not, the guard sends them to /login. Roles 3 and 6 are in the list because they are legitimate platform operators of the queue console.
  • src/components/auth/ProtectedRoute.tsx checks that the user is authenticated and holds at least one queue organization; if not, they are sent to /setup-org. It waits for the organization query to settle before deciding.
Fail-open behaviour in ProtectedRoute (Annex B #32)

When the organization query errors, ProtectedRoute returns true for hasOrg and lets the user through: orgsError ? true : false (src/components/auth/ProtectedRoute.tsx:48-52). That was a deliberate availability choice, because a brief backend failure should not lock operators out of a live queue, but it is a fail-open condition and is marked Open under Annex B #32. It does not bypass authentication (the session check still runs first) or backend authorization, and it only affects the client's organization-setup gate. The fix is to tell an authorization failure (redirect) apart from a transport failure (show a retryable error, not the app).

The backend is the enforcement boundary, stated explicitly

The route guards are a UI safety control, not an authorization boundary. A user who forges their stored profile or calls the API directly still has to be denied by the backend, which must:

  • take roleId/statusId from the session and never from the request body (the client sends them for legacy reasons, see §5.1);
  • scope every queue-organization query and mutation to the cookie identity;
  • authorize every organization and queue identifier against the session's memberships.

Until the backend team shows this, Annex B #23, #24, #27 and #28 stay open.

6.3 Per-action checks

Each action exposes only what the role permits, so for example bid approval appears just to role 11 in the bidding board. Every mutating request goes to the backend, and the backend alone accepts or rejects it. No client-side decision is treated as final.

6.4 Privilege categories and lifecycle

The code implements privilege categorization (INSA 2.5.D) through the role set above and the queue-organization membership model. Granting and revoking access, and rotating credentials on a fixed schedule, are organizational procedures that are not evidenced in this repository (INSA 2.5.C and 2.5.E).

7. Transport security

7.1 HTTPS

The production URL is HTTPS-only (queue.dynamicsroute.tech). In development the application is set to call the API over https:// (VITE_API_BASE_URL=https://dev.dynamicsroute.tech), and a production build defaults to the same-origin /api path, which inherits the page's TLS. The socket client targets the same host and sends the cookie with withCredentials: true.

Not independently verified for this submission

This repository contains no server configuration, so the HTTP-to-HTTPS redirect, the TLS protocol and cipher set, and the certificate chain on the production host were not independently assessed here. The application itself only ever addresses HTTPS origins in production. Annex B #13 and #15 are marked Pass on the basis of the application's own transport choices (HTTPS/WSS and no mixed content); #14 is marked Pass with the platform redirect noted as unverified; #16 (HSTS) and #17–#18 (TLS/certificate) are Open.

7.2 Socket transport

src/lib/socket.ts initializes Socket.IO with transports: ["websocket", "polling"], withCredentials: true, reconnectionAttempts: 5, reconnectionDelay: 1500, reconnectionDelayMax: 5000 and timeout: 20000. The polling fallback is kept for restrictive networks. Unlike a client pinned to WebSocket only, the polling handshake is an ordinary HTTP request, so it also has to be protected by the platform's cookie and CSRF controls.

7.3 HSTS and cookie scope

No Strict-Transport-Security header is defined anywhere in the repository, so HSTS is absent (Annex B #16). Because a production build defaults to a same-origin API path, the session cookie may be same-site. If the deployment instead splits the SPA and API across registrable domains, the cookie has to be SameSite=None; Secure and CSRF defence cannot rely on the default SameSite=Lax (see §5.3 and §14 #61, #62). The deployment and the backend have to settle this before submission.

8. Application security controls

8.1 Content-Security-Policy

There is no CSP, stated plainly

A scan of the whole repository (src/, public/, index.html, vite.config.ts) found no Content-Security-Policy: no meta tag, no build-time injection, and no server configuration to deliver a header. This asset sends the browser no script-execution policy at all. Annex B #83 (non-specific content types), #85 (anti-sniffing) and #96 (anti-clickjacking) are therefore Open, and there is no defence-in-depth layer behind React's output encoding for Annex B #43.

One thing to account for later: index.html embeds an inline <script type="application/ld+json"> structured-data block. A strict script-src policy would need to accommodate it with a hash or nonce, or the block would have to move to an external file. That is recorded as a dependency of the remediation in §17.

8.2 Security response headers

This repository configures no security response headers: X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy are all missing. The hosting platform may add some of them, but that sits outside this asset and is not evidenced. They are recorded as hosting items in §16.

8.3 Client-side output encoding

  • React escaping. Every untrusted value goes through JSX text nodes and attribute bindings, which React escapes by default (Annex B #43).
  • No raw HTML sinks. A source scan found no dangerouslySetInnerHTML, innerHTML, eval, new Function or document.write in src/.
  • Input sanitisation. Zod transforms strip HTML tags and control characters from names, addresses and emails before they are stored or sent (src/schemas/queue.ts: stripTags, stripCtrl, sanitizeText, sanitizeEmail).

Without a CSP these controls are the only thing standing between script injection and the browser, which is why §17 asks for a policy as the first server-side change.

8.4 Build hardening

  • Sourcemap suppression. vite.config.ts sets build.sourcemap = process.env.NODE_ENV !== "production", so development builds carry sourcemaps and production builds do not. The effect is right, but it is implicit; pinning an explicit false for production is recommended (Annex B #6).
  • No secrets in the bundle. Only public configuration (API and socket hosts) is pulled in from environment variables. No API keys or credentials are embedded or committed.

9. Input validation and data handling

9.1 Form validation and sanitisers

Forms use react-hook-form with zod schemas (src/schemas/queue.ts) for login, registration, organization setup, check-in and dispatch. The schemas constrain length and format, and they transform the values: strip HTML tags (stripTags), drop non-printable control characters (stripCtrl), collapse whitespace (sanitizeText) and normalise email (sanitizeEmail). Phone numbers are normalised to E.164 (+251…) by src/utils/phoneFormatter.ts and src/lib/authConfig.ts. Client-side validation is a usability and hygiene control only, and the backend has to re-validate every field.

9.2 File uploads

No file upload feature

The console neither uploads nor downloads files: a source scan found no FormData, no file input, no FileReader and no multipart request. The Annex B File Upload group (#78–#82) is therefore marked N/A for this asset. If uploads are added later, for example for compliance documents, the validation and storage controls have to be designed and added to this document.

9.3 Production error handling and log hygiene

Finding: raw error logging is not dev-gated

src/utils/parseError.ts runs console.error("[parseError]", error) unless the caller passes { silent: true }, and it is not gated behind import.meta.env.DEV. The logged error object can include the request configuration and response data, which for auth calls can carry the phone number and OTP. That is a production information-disclosure and log-hygiene gap. It is why Annex B #4 (sensitive information in logs/errors) and #77 (disclosure of tokens in logs) are marked Open, and it also contributes to #7.

The path shown to the user is better: parseError returns mapped, generic messages per HTTP status (401 → "Session expired", 403 → "You do not have permission", and so on). But when the backend sends a message/error string it is passed through to the user (resolveServerMsg), which can reveal internal detail. Restricting this to an allow-list of server messages would close it.

9.4 Client-side data and PII handling

The session JWT lives only in the httpOnly cookie, while localStorage holds the non-secret profile (queueadmin:user: name, phone, email, role) used for rendering. Logout calls clearAuth(), which removes that profile from both localStorage and sessionStorage. Other local keys (app_language, queueadmin:store, a UI selection only, insa_security_checklist_v1, theme and sidebar preferences) hold no personal data and are left alone; that is acceptable, though it is noted here for completeness. The remaining risk is that the profile sits in cleartext while the user is signed in. That was a deliberate routing decision and it is recorded in §16.

11.2 Static analysis and security linting

The ESLint configuration (eslint.config.mjs) pulls in @eslint/js, typescript-eslint, eslint-plugin-react and eslint-plugin-react-hooks, and nothing else. There is no security plugin (no eslint-plugin-security), so risky patterns such as non-literal regular expressions, timing comparisons or unsafe object injection never get flagged. oxlint is installed and configured, but it is not a security gate. The lint script runs eslint . --ext ts,tsx --max-warnings 0, yet the README describes npm run lint as oxlint, so the documentation and the script disagree.

11.3 A gap: unused and mis-declared dependencies

  • @tanstack/react-query is listed in package.json but nothing imports it; the project uses RTK Query. It is dead weight that widens the attack surface and the audit scope for no benefit.
  • .npmrc sets legacy-peer-deps=true, which suppresses peer dependency resolution and makes the install graph harder to reproduce.

11.4 Continuous integration

No CI today

There is no .github/ directory, no Dependabot configuration, no secret scanning and no build pipeline. Nothing catches dependency drift, checks that a rebuild stays clean on deploy, or runs the test suite (107 tests, all passing) automatically. A suggested workflow is in §17.

17. Security recommendations and roadmap

The remediation is phased by how much risk each phase removes for the effort it costs. Phases 1–4 are code-only and independent of the platform decision; Phase 0 and Phase 6 need hosting or backend action and carry the highest impact. The recommended order is Phase 1 → Phase 2 → Phase 3 → Phase 4, with Phase 0 started immediately in parallel.

Phase 0 — Server/header layer (highest impact; needs hosting access)

Put a CSP and security-header layer on queue.dynamicsroute.tech. The policy has to account for the inline JSON-LD block in index.html (hash or nonce, or move the block to an external file). The recommended header set: Content-Security-Policy (with frame-ancestors 'none'), Strict-Transport-Security, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, Permissions-Policy, COOP/CORP, a Cache-Control policy (no-store on HTML, immutable on hashed assets), method restriction, and 404 blocks for /.env, /.git and *.map.
