How to read this document

§3 contains the numbered functional requirements (prefix FR-), grouped by application area, each with a priority and a Source citation to the file that implements it. §4 contains the non-functional requirements (NFR-). §7 defines the queue, bidding and status business rules that most functional requirements refer to, and states plainly which decisions are made by the console and which are enforced by the backend (transportBackEndNative) as the system of record. Requirement identifiers are stable and are referenced by the SDD and by the test evidence, so a reviewer can trace a requirement to its design element and to its implementation.

Client-authority note

Dynamics Queue Admin is a client of the Dynamics backend. Authentication state, queue ordering, geofence decisions, bidding gate state, bid ranking and offer acceptance are authoritative on the server. The console renders that state and issues requests; it holds no independent authority over marketplace business data (§7.4).

1. Introduction

1.1 Purpose

This document specifies the requirements of Dynamics Queue Admin 1.0.0, the single-page web console used to operate a loading place (a Queue Organization) on the Dynamics freight marketplace. It is written for the submitting entity's own development and test baseline and for external review, and forms part of the submission package for the Information Security Authority's website review against the INSA Secure Website Management Standard (Version 1.0, 2014 EC).

1.2 Scope

Dynamics Queue Admin provides three jobs: (a) loading-place management — creating and administering a Queue Organization profile, its coordinates and optional check-in radius, its approval status, and its members (roles 11 and 12); (b) the FIFO driver queue — proving driver presence by GPS check-in and placing arrivals into a first-in-first-out line per vehicle type, then dispatching, overriding, removing and auditing entries; and (c) bidding on the shipper's behalf — approving or closing bidding per order and accepting a driver's bid on the shipper's behalf using explicit identifiers. It also covers a dashboard over all organizations, derived reporting, real-time synchronization, a security-compliance dashboard, localization (English and Amharic) and dark mode.

Out of scope: the Dynamics backend (transportBackEndNative), which is the system of record; the driver mobile application; the shipper application; and the operations and administrator dashboards. These are separate systems with separate requirements documents. All business logic of record — queue ordering, the check-in geofence, the bidding gate, journey status and offer acceptance — is held and enforced by the backend; this console is a client of that record and holds no authority over it (§7.4).

2. Overall description

2.1 Product perspective

Dynamics Queue Admin is one console in the Dynamics freight marketplace, a multi-application product. The marketplace backend (transportBackEndNative) is the system of record and exposes REST (/api) and Socket.IO interfaces. Drivers use a mobile application to check in, bid and update journey status; shippers use a separate application to create freight requests. This console is the dispatch side: it operates the physical loading place that drivers queue at and that shippers' requests are matched to. It is a single-page React application served as a static site at queue.dynamicsroute.tech.

2.2 User classes and characteristics

User class Role id Characteristics and primary tasks
Queue Org Admin 11 Primary administrator of a loading place. Creates and edits the organization profile (coordinates, radius, type), manages members, and approves or closes bidding per order. Long-lived session (365 days).
Queue Dispatcher 12 Runs the daily queue. Manually checks drivers in, dispatches queued entries to requests, overrides position or removes entries with a reason, and reviews entry history. Long-lived session (365 days).
Admin 3 Platform administrator. Approves, rejects or suspends loading places and oversees all organizations. Short session (24 hours).
Super Admin 6 Platform super-administrator. Same oversight and approval powers as Admin across all organizations. Short session (24 hours).

All four classes are authenticated by phone number plus OTP and gated by the guard stack (ProtectedRoute then RoleGuard, which admits roles {11, 12, 3, 6}). Client-side role checks are a usability boundary only; the backend re-checks role and membership on every request.

2.3 Operating environment

  • Runtime: a modern evergreen browser executing a Vite-built React 19 SPA (ES modules, dynamic import for route chunks).
  • Network: HTTPS to queue.dynamicsroute.tech; REST and Socket.IO to the backend host. Session cookie is httpOnly/SameSite and requires credentials: "include".
  • Storage: localStorage for non-sensitive preferences only (queueadmin:user profile, app_dark_mode, app_language, persisted selectedOrgId); no token is ever stored.
  • Optional external service: the Photon geocoder for order-place search (VITE_PHOTON_URL), with a built-in Ethiopian-cities fallback.

2.4 Design and implementation constraints

  • Backend authority: the console must not compute or invent authoritative identifiers (queue numbers, bid ids, membership ids); it must use values returned by the backend and send them back explicitly (see FR-BID and §7.4).
  • Cookie session: a JWT must not be placed in JavaScript-accessible storage; getToken() returns null by design.
  • Role-resolved sign-in: the login and OTP endpoints must be called without a roleId so that the backend resolves the account's own role and a role-12 dispatcher can sign in.
  • Single API source of truth: endpoint paths must live in src/utils/constant.ts; feature modules must not hard-code paths.
  • Hand-written CSS only: no utility framework; design tokens live in src/index.css with a src/dark.css dark theme.

2.5 Assumptions and dependencies

  • The backend enforces authentication, role and membership on every request.
  • The backend issues and validates the session cookie over HTTPS with SameSite attributes.
  • The backend exposes the Socket.IO event fan-out under the queueOrgAdmin identity for queue staff and admin for platform admins.
  • The backend performs geofence evaluation for GPS check-in using the organization's coordinates and checkinRadiusKm.
  • The Photon geocoder is optional; when unavailable, place search falls back to a built-in city list.
  • The hosting environment terminates TLS and, where the INSA standard requires it, applies HTTP security headers (no CSP is configured in this repository; see §7.5).

2.6 Stakeholders and external actors

Actor / system Interest
Queue Org Admin (11) Operate the loading place; control bidding; manage members.
Queue Dispatcher (12) Keep the physical queue accurate and fair (FIFO).
Admin (3) / Super Admin (6) Approve and oversee loading places across the marketplace.
Driver / vehicle owner Fair queue position; visible bid outcomes via the driver application.
Shipper Receive a dispatched driver or an accepted bid for their request.
Backend REST API System of record; authoritative business rules and identifiers.

5.2.1 Authentication and session contract

  • The primary session is an httpOnly cookie set by the backend at POST /api/user/verifyUserByOTP. The client never reads or stores a JWT (getToken() returns null).
  • Every request sends the cookie with credentials: "include"; no Authorization header is set.
  • There is no refresh-token flow: any 401 dispatches a global logout in the RTK Query base query, and the axios interceptor clears auth and routes to /login.
  • Session lifetime is role-based on the backend: roles 3 and 6 = 24 hours; roles 11, 12 and others = 365 days.

5.2.2 Socket.IO protocol

The client connects with withCredentials and an auth payload of { user, phoneNumber }. The socket identity is derived from the account role: roles 3 and 6 map to admin; queue staff (roles 11 and 12) share a single queueOrgAdmin identity because the backend fan-out keys queue events under that identity for both roles. Subscriptions use queue:subscribe / queue:unsubscribe with a reference-counted room keyed by queueOrganizationUniqueId (and optional queueDate); rooms are re-subscribed on (re)connect. Inbound events are parsed for a messageTypes value; acknowledgements and ping/pong are ignored. Organization events invalidate QueueOrganizations after 100 ms; all other queue events invalidate QueueStatus, DriverQueue and ShipperRequests after 250 ms. A rejected handshake ends the session.

5.2.3 Error-handling contract

src/utils/parseError.ts normalizes axios errors, RTK Query errors, serialized errors and generic throws into one human-readable message, reading server message/error/details/validation fields and mapping HTTP status codes to fallbacks. 401 means "session expired — log in again" and triggers logout; 403 means "authenticated but not permitted" and is shown as a permission error without logging out.

5.2.4 Optional third-party service

Place search for order origin/destination uses the Photon geocoder (VITE_PHOTON_URL, default https://photon.komoot.io/api/) merged with a built-in list of Ethiopian cities and a local fallback. No map tiles or routing calls are made by this console.

5.3 Hardware interfaces

No dedicated hardware is required. The console needs a device with a modern browser and network access. An optional device geolocation capability is used only to compute an on-screen proximity cue; the authoritative check-in geofence is evaluated by the backend.

5.4 Communications interfaces

  • HTTPS (TLS) to the SPA host and the backend REST API.
  • WebSocket (Socket.IO) for realtime queue and organization events.
  • Cookies: the httpOnly/SameSite session cookie, sent with credentials: "include".
  • SMS: OTP delivery, performed by the backend and the telecom provider.

6.3 Data flow

UI actions invoke RTK Query hooks/mutations or legacy axios services. The base query resolves the API prefix from VITE_API_BASE_URL/VITE_API_URL (normalized to end in /api) and sends the httpOnly cookie via credentials: "include". Responses populate the RTK Query cache; socket events trigger debounced tag invalidation that refetches affected queries. Client state (auth profile, selected organization, theme, language, socket flag) lives in Redux slices, zustand, React Context and localStorage; no token is ever placed in JavaScript-accessible storage.

6.4 Data validation constraints

  • Phone numbers are normalized to +251 plus nine digits.
  • Latitude is constrained to [-90, 90] and longitude to [-180, 180].
  • Vehicle quantities are positive integers; greater-than-nine individual requests are coerced to batch (company_target).
  • UUID and enum fields are validated against their allowed forms before submission.
  • Text and email inputs are sanitized (tags, control characters and whitespace collapsed).

7.2 Bidding business rules

ID Rule Authority
BR-B-01 Bidding is gated per order, not per batch; each order carries its own approval flag. Backend; the console toggles and displays per order.
BR-B-02 Only orders whose journey status is 1 are eligible for bidding / dispatch. Backend; the console filters the selector.
BR-B-03 Bids are ranked and returned cheapest-first by the backend. Backend; the console renders the order as returned.
BR-B-04 Accepting a bid requires the explicit shipperRequestUniqueId and driverRequestUniqueId (optional journeyDecisionUniqueId). Backend; the console sends the exact ids.
BR-B-05 A missing or invalid identifier is a hard failure; identifiers are never reconstructed, guessed or fuzzy-matched. Client rule enforced in the accept hook; backend rejects invalid ids.
BR-B-06 Only the Queue Org Admin role (11) is presented with bidding approval controls. Backend enforces; the console gates the control.

7.5 Declared limitations

The following are known, deliberate or deferred limitations of version 1.0.0, stated honestly for the reviewer. None of them is represented elsewhere in this document as a capability.

Item Status Detail / planned action
No refresh-token flow Noted Any expiration ends the session (401 → logout); add refresh only if the backend offers it.
Role-dependent session lifetime By design Roles 3/6 = 24 hours; roles 11/12 and others = 365 days, set by the backend.
Unused @tanstack/react-query dependency Open Nothing imports it; remove from package.json.
Settings profile / notifications / 2FA disabled Noted No profile-update or notification/2FA backend; controls are disabled with a visible explanation rather than faked.
Dashboard counts computed client-side Noted Metrics derive from fetched lists (limit 100) in the browser; move to server aggregates for scale.
Socket payloads trigger refetch only By design Events invalidate tags; no per-event cache patching is applied.
Manual check-in merges directory with current queue By design The picker merges the driver directory with the current queue to avoid duplicates.
Unreachable /organizations page Open The route redirects to /dashboard; the standalone page is not reachable and should be deleted or re-wired.
No CSP or HTTP security headers in this repo Deferred Server-level control outside this code asset; mitigate at the hosting / reverse-proxy layer.
No in-app error boundary Open Add a top-level React error boundary to contain render errors.
localStorage holds non-sensitive profile only By design No token is stored; legacy token records are purged on read.
