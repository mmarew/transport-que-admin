Client-authority note

Dynamics Queue Admin is a client of the Dynamics backend. Authentication state, queue ordering, geofence decisions, bidding gate state, bid ranking and offer acceptance are authoritative on the server. The console renders that state and issues requests; it holds no independent authority over marketplace business data (§7.4).

1. Introduction

1.1 Purpose

This document specifies the requirements of Dynamics Queue Admin 1.0.0, the single-page web console used to operate a loading place (a Queue Organization) on the Dynamics freight marketplace. We wrote it for our own development and test baseline and for external review. It forms part of the submission package for the Information Security Authority's website review against the INSA Secure Website Management Standard (Version 1.0, 2014 EC).

1.2 Document conventions

  • Requirement identifiers. Functional requirements are identified FR-<AREA>-NN and non-functional requirements NFR-<AREA>-NN (for example FR-QUE-09, NFR-SEC-06). Identifiers are stable and are not reused when a requirement is withdrawn.

  • Obligation keywords. "shall" states a binding requirement, "should" a recommendation and "may" an option. All requirements in §3 and §4 are stated with "shall".

  • Models. Diagrams in §6 are authored as Mermaid sources under docs/insa/assets/ and numbered Figure 6.x; each model is traceable to the requirement families it elaborates.
  • Typographic conventions. Monospace marks identifiers, paths and values. Amber highlighted text marks an honest limitation or a server/hosting-owned control rather than a defect.

1.4 Scope

Dynamics Queue Admin does three jobs. First, loading-place management: creating and administering a Queue Organization profile, its coordinates and optional check-in radius, its approval status, and its members (roles 11 and 12). Second, the FIFO driver queue: proving driver presence by GPS check-in and placing arrivals into a first-in-first-out line per vehicle type, then dispatching, overriding, removing and auditing entries. Third, bidding on the shipper's behalf: approving or closing bidding per order and accepting a driver's bid on the shipper's behalf using explicit identifiers. It also covers a dashboard over all organizations, derived reporting, real-time synchronization, a security-compliance dashboard, localization (English and Amharic) and dark mode.

Out of scope: the Dynamics backend (transportBackEndNative), which is the system of record; the driver mobile application; the shipper application; and the operations and administrator dashboards. These are separate systems with separate requirements documents. All business logic of record (queue ordering, the check-in geofence, the bidding gate, journey status and offer acceptance) lives in and is enforced by the backend. This console is a client of that record and holds no authority over it (§7.4).

2. Overall description

2.1 Product perspective

Dynamics Queue Admin is one console in the Dynamics freight marketplace, which is a multi-application product. The marketplace backend (transportBackEndNative) is the system of record and exposes REST (/api) and Socket.IO interfaces. Drivers use a mobile application to check in, bid and update journey status; shippers use a separate application to create freight requests. This console is the dispatch side: it operates the physical loading place that drivers queue at and that shippers' requests are matched to. It is a single-page React application served as a static site at queue.dynamicsroute.tech.

2.2 Product features and functions

The console's major feature groups are listed below. Each is elaborated as numbered requirements in §3 and modelled in §6; the letters in brackets are the requirement prefixes.

2.3 User classes and characteristics

User class Role id Characteristics and primary tasks
Queue Org Admin 11 Primary administrator of a loading place. Creates and edits the organization profile (coordinates, radius, type), manages members, and approves or closes bidding per order. Long-lived session (365 days).
Queue Dispatcher 12 Runs the daily queue. Manually checks drivers in, dispatches queued entries to requests, overrides position or removes entries with a reason, and reviews entry history. Long-lived session (365 days).
Admin 3 Platform administrator. Approves, rejects or suspends loading places and oversees all organizations. Short session (24 hours).
Super Admin 6 Platform super-administrator. Same oversight and approval powers as Admin across all organizations. Short session (24 hours).

All four classes sign in with a phone number plus OTP and pass through the same guard stack (ProtectedRoute then RoleGuard, which admits roles {11, 12, 3, 6}). Client-side role checks are a usability boundary only; the backend re-checks role and membership on every request.

2.4 Operating environment

  • Runtime: a modern evergreen browser executing a Vite-built React 19 SPA (ES modules, dynamic import for route chunks).
  • Network: HTTPS to queue.dynamicsroute.tech; REST and Socket.IO to the backend host. Session cookie is httpOnly/SameSite and requires credentials: "include".
  • Storage: localStorage for non-sensitive preferences only (queueadmin:user profile, app_dark_mode, app_language, persisted selectedOrgId); no token is ever stored.
  • Optional external service: the Photon geocoder for order-place search (VITE_PHOTON_URL), with a built-in Ethiopian-cities fallback.

2.5 Design and implementation constraints

  • Backend authority: the console must not compute or invent authoritative identifiers (queue numbers, bid ids, membership ids); it must use values returned by the backend and send them back explicitly (see FR-BID and §7.4).
  • Cookie session: a JWT must not be placed in JavaScript-accessible storage; getToken() returns null by design.
  • Role-resolved sign-in: the login and OTP endpoints must be called without a roleId so that the backend resolves the account's own role and a role-12 dispatcher can sign in.
  • Single API source of truth: endpoint paths must live in src/utils/constant.ts; feature modules must not hard-code paths.
  • Hand-written CSS only: no utility framework; design tokens live in src/index.css with a src/dark.css dark theme.

2.6 User documentation

The following user-facing documentation ships with, or is generated from, the console:

  • End User Guide, a task-oriented guide (docs/insa/UserGuide.html, delivered as UserGuide.pdf) covering sign-in, loading-place setup, membership, the FIFO queue, bidding, orders, reporting, settings and the security dashboard.
  • Contextual in-app help: labels, tooltips, inline validation messages (driven by zod schemas) and empty-state guidance within the console itself.
  • Security compliance view, which presents the INSA standard content and the security checklist in-console (src/data/insaStandard.ts) so operators can read the obligations they are expected to meet.

Delivered formats are HTML (for review) and PDF (for submission). There is no printed manual; the guide lives in the repository alongside this specification.

2.7 Assumptions and dependencies

  • The backend enforces authentication, role and membership on every request.
  • The backend issues and validates the session cookie over HTTPS with SameSite attributes.
  • The backend exposes the Socket.IO event fan-out under the queueOrgAdmin identity for queue staff and admin for platform admins.
  • The backend performs geofence evaluation for GPS check-in using the organization's coordinates and checkinRadiusKm.
  • The Photon geocoder is optional; when unavailable, place search falls back to a built-in city list.
  • The hosting environment terminates TLS and, where the INSA standard requires it, applies HTTP security headers (no CSP is configured in this repository; see §7.5).

5.2.1 Authentication and session contract

  • The primary session is an httpOnly cookie set by the backend at POST /api/user/verifyUserByOTP. The client never reads or stores a JWT (getToken() returns null).
  • Every request sends the cookie with credentials: "include"; no Authorization header is set.
  • There is no refresh-token flow: any 401 dispatches a global logout in the RTK Query base query, and the axios interceptor clears auth and routes to /login.
  • Session lifetime is role-based on the backend: roles 3 and 6 = 24 hours; roles 11, 12 and others = 365 days.

5.2.2 Socket.IO protocol

The client connects with withCredentials and an auth payload of { user, phoneNumber }. Socket identity comes from the account role: roles 3 and 6 map to admin, while queue staff (roles 11 and 12) share a single queueOrgAdmin identity because the backend fan-out keys queue events under that identity for both roles. Subscriptions use queue:subscribe / queue:unsubscribe with a reference-counted room keyed by queueOrganizationUniqueId (and optional queueDate); rooms are re-subscribed on (re)connect. Inbound events are parsed for a messageTypes value, and acknowledgements and ping/pong are ignored. Organization events invalidate QueueOrganizations after 100 ms; all other queue events invalidate QueueStatus, DriverQueue and ShipperRequests after 250 ms. A rejected handshake ends the session.

5.2.3 Error-handling contract

src/utils/parseError.ts normalizes axios errors, RTK Query errors, serialized errors and generic throws into one human-readable message, reading server message/error/details/validation fields and mapping HTTP status codes to fallbacks. 401 means "session expired, log in again" and triggers logout; 403 means "authenticated but not permitted" and is shown as a permission error without logging out.

5.2.4 Optional third-party service

Place search for order origin/destination uses the Photon geocoder (VITE_PHOTON_URL, default https://photon.komoot.io/api/) merged with a built-in list of Ethiopian cities and a local fallback. The console makes no map-tile or routing calls.

5.3 Hardware interfaces

There is no dedicated hardware requirement: any device with a modern browser and network access works. Device geolocation is optional and is used only to compute an on-screen proximity cue; the backend evaluates the authoritative check-in geofence.

5.4 Communications interfaces

  • HTTPS (TLS) to the SPA host and the backend REST API.
  • WebSocket (Socket.IO) for realtime queue and organization events.
  • Cookies: the httpOnly/SameSite session cookie, sent with credentials: "include".
  • SMS: OTP delivery, performed by the backend and the telecom provider.

6.2 Sequence diagrams

6.2.1 Registration, sign-in and session. A first-time Queue Org Admin is registered by calling POST /api/user/createUser with backend role 11. A returning user signs in with a phone number via POST /api/user/loginUser, which dispatches an OTP; the OTP is verified with POST /api/user/verifyUserByOTP. Neither the login nor the verify call sends a roleId, so the backend resolves the account's own role and a role-12 dispatcher can sign in. On success the backend opens an httpOnly SameSite session cookie; the console persists only the non-secret userData profile. Any 401 later triggers a single global logout (FR-AUTH, NFR-SEC).

6.2.2 Queue check-in and real-time synchronization. The operator searches the driver directory (GET /api/queue/driverDirectory), selects a driver and vehicle, the input is validated with a zod schema, and the check-in is sent with explicit identifiers to POST /api/queue/manualCheckin. The backend returns the server-issued queueNumber that fixes the FIFO position; the console then refetches the snapshot and, on a Socket.IO event, invalidates and refetches the affected views. Dispatch, override and removal are sent as status actions (FR-QUE, FR-NOTIF).

6.3 Activity diagrams

6.3.1 FIFO queue lifecycle. The queue activity begins with a snapshot fetch for a date. Manual check-in is offered only when the organization is approved and the queue is enabled; the backend assigns the authoritative FIFO position and the console preserves that server order rather than reordering locally. Operator actions move an entry to dispatched, overridden or removed, each writing an audit record (FR-QUE).

6.3.2 Bidding gate. For a shipper request, the bidding gate is applied per order: the operator approves or closes bidding via POST /api/queue/bidding/approve, reviews the authoritative bids (GET /api/queue/bidding/order/:id/bids) ranked cheapest-first, and the backend independently enforces the approval permission. The console holds no independent authority over the gate (FR-BID).

7.3 Data flow

UI actions invoke RTK Query hooks/mutations or legacy axios services. The base query resolves the API prefix from VITE_API_BASE_URL/VITE_API_URL (normalized to end in /api) and sends the httpOnly cookie via credentials: "include". Responses populate the RTK Query cache; socket events trigger debounced tag invalidation that refetches affected queries. Client state (auth profile, selected organization, theme, language, socket flag) lives in Redux slices, zustand, React Context and localStorage. No token is ever placed in JavaScript-accessible storage.

7.4 Data validation constraints

  • Phone numbers are normalized to +251 plus nine digits.
  • Latitude is constrained to [-90, 90] and longitude to [-180, 180].
  • Vehicle quantities are positive integers; greater-than-nine individual requests are coerced to batch (company_target).
  • UUID and enum fields are validated against their allowed forms before submission.
  • Text and email inputs are sanitized (tags, control characters and whitespace collapsed).

8. Business rules and status model

8.1 Queue business rules

ID Rule Authority
BR-Q-01 A driver's presence at the loading place is proven by GPS check-in; the geofence compares the driver's position against the organization's coordinates within checkinRadiusKm (default 15 km; 0 disables the gate). Backend (server-authoritative); the console shows a Haversine proximity cue only.
BR-Q-02 Queue order is strictly first-in-first-out by the server-issued queueNumber within each vehicle type. Backend (issues the number); the console preserves and displays it.
BR-Q-03 An entry may be positioned by an override, which requires a reason and is written to the backend audit trail. Backend (audits); the console collects the reason.
BR-Q-04 An entry may be removed; removal is audited and reversible only through a new check-in. Backend; the console requests removal after confirmation.
BR-Q-05 A queue entry may carry a targetedShipperUserUUID that reserves the driver for one shipper; it is carried through dispatch as the shipper target. Backend; the console displays and forwards it.
BR-Q-06 Only an approved organization with the queue enabled may accept check-ins and dispatches. Backend; the console hides the affordances where it can detect the state.

8.2 Bidding business rules

ID Rule Authority
BR-B-01 Bidding is gated per order, not per batch; each order carries its own approval flag. Backend; the console toggles and displays per order.
BR-B-02 Only orders whose journey status is 1 are eligible for bidding / dispatch. Backend; the console filters the selector.
BR-B-03 Bids are ranked and returned cheapest-first by the backend. Backend; the console renders the order as returned.
BR-B-04 Accepting a bid requires the explicit shipperRequestUniqueId and driverRequestUniqueId (optional journeyDecisionUniqueId). Backend; the console sends the exact ids.
BR-B-05 A missing or invalid identifier is a hard failure; identifiers are never reconstructed, guessed or fuzzy-matched. Client rule enforced in the accept hook; backend rejects invalid ids.
BR-B-06 Only the Queue Org Admin role (11) is presented with bidding approval controls. Backend enforces; the console gates the control.
